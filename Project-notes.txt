Concepts used in `Instrument.java` and `InstrumentRepository.java`:

 📌 1. `Instrument.java` (Entity Class)

 ✅ Purpose: This class represents a *database table* in JPA/Hibernate. Each row in the `instrument` table will map to an instance of this class.

🔹 Key Annotations
1.`@Entity`
	* Marks this class as a *JPA entity* (a persistent object that Hibernate maps to a database table).
	* Without this, Hibernate won’t recognize it.

2.`@Table(name = "instrument")`
	* Specifies the table name in DB (`instrument`).
	* If omitted, Hibernate would use the class name (`instrument`) by default (case-sensitive depending on DB).

---
🔹 Lombok Annotations
3. `@Getter` → generates getters for all fields.
4. `@Setter` → generates setters for all fields.
5. `@NoArgsConstructor` → generates a no-argument constructor.
6. `@AllArgsConstructor` → generates a constructor with all fields.
7. `@Builder` → lets us use *builder pattern* (useful when creating objects in service/test code).

👉 These remove boilerplate code (industry best practice).
👉 Example:
```java
Instrument i = Instrument.builder()
    .isin("US1234567890")
    .ticker("AAPL")
    .currency("USD")
    .build();
```
---
🔹 Field-Level Mappings

8. `@Id`
	* Marks the *primary key*.

9. `@GeneratedValue(strategy = GenerationType.IDENTITY)`
	* Auto-generates the PK using the DB’s identity column (Postgres `BIGSERIAL`).
	* `IDENTITY` is common in Postgres & MySQL.

10. `@Column(...)`
	* Fine-tunes how fields map to table columns.
	* `length` → max size of VARCHAR.
	* `nullable = false` → cannot be null.
	* `unique = true` → adds DB constraint for uniqueness.
	* `name = "created_at"` → sets custom column name.
	
🔹 Timestamps (`createdAt`, `updatedAt`)
	* `LocalDateTime` → represents timestamp in Java.
	* `updatable = false` → prevents Hibernate from modifying `createdAt`.

🔹 Entity Lifecycle Callbacks

11. `@PrePersist`
	* Runs before entity is *inserted* into DB.
	* Here we set `createdAt` and `updatedAt` to `now()`.

12. `@PreUpdate`
	* Runs before entity is *updated*.
	* Updates `updatedAt`.
	👉 This ensures *audit fields* are auto-populated without manual code.

 *Entity* → maps Java object to DB table.

✅ Concepts Covered in `InstrumentService`

1. *Service Layer Pattern*

   * We introduced a dedicated *`InstrumentService`* class instead of directly calling the repository from the controller.
   * This follows the *Service Layer Design Pattern*, widely used in enterprise apps.
   * Benefits:
     * Keeps *business logic separate* from API layer.
     * Makes unit testing easier (mock the service independently).
     * Allows scaling later (e.g., add caching, validations, events in service without touching controller).

2. *Dependency Injection (Constructor Injection)*
   ```java
   private final InstrumentRepository instrumentRepository;

   public InstrumentService(InstrumentRepository instrumentRepository) {
       this.instrumentRepository = instrumentRepository;
   }
   ```

    * Spring injects the `InstrumentRepository` bean into the service.
    * *Constructor injection* (preferred way) makes the class *immutable* and easier to test.
    * Avoids pitfalls of *field injection (@Autowired)* like hidden dependencies.

3. *Spring Data JPA Usage*
    * Service calls `instrumentRepository.save()` / `findAll()` / `findById()` → these come from Spring Data JPA.
    * No need to write SQL → repository interfaces + JPA do it for us.
    * Service is thin here but can grow to handle business validations (e.g., “ISIN must be unique”).

4. *Optional<T>*
   ```java
   public Optional<Instrument> getInstrumentById(Long id)
   ```
   * We return `Optional` from repository/service to handle “record not found” cases safely instead of null.
   * Prevents `NullPointerException` and forces caller to handle missing values.

Importants:

1. Why DTO Layer?
	Entities (JPA classes) = mirror your DB tables. They may have sensitive fields (password, audit, internal IDs). Exposing them directly in REST = risky.
	DTOs (Data Transfer Objects) = safe “API contract”. You decide what goes in (request DTO) and what goes out (response DTO).

👉 Example:
	A POST /instruments RequestDTO should not contain id, createdAt.
	A GET /instruments ResponseDTO can include those (read-only).

	So DTOs decouple API from DB model. Tomorrow if DB schema changes, your API contract stays stable. That’s why industry projects always use DTOs.


3. then Why Service Layer?
	The Service Layer is where business logic lives.
	Controllers should only handle HTTP stuff. Services handle rules like:
	“Before saving an instrument, check if ISIN already exists.”
	“When deleting, also publish a Kafka event.”
	“Audit who made the change.”

👉 If we let Controllers call Repositories directly, APIs would get bloated with business logic.

Flow in One Line (API call path):
	➡️ Controller (HTTP Request) → DTO Validation → Mapper (DTO → Entity) → Service (business logic) → Repository (DB) → Back to Service → Mapper (Entity → DTO) → Controller (HTTP Response).

👉 Flow:
	 Request JSON → InstrumentRequestDto (validated with annotations).
	Controller → calls InstrumentMapper.toEntity(requestDto).
	Service → instrumentRepository.save(entity) persists to DB.
	Service returns Entity → mapped via InstrumentMapper.toDto(entity).
	Controllerreturns ResponseEntity → API responds with JSON including id, createdAt, updatedAt.

✅ Now you have a proper enterprise-grade flow:
	DTO = API contract
	Mapper = conversion layer
	Service = business logic
	Controller = request/response

---
 1. Why Exception Handling Layer?
	* In a real system, *things go wrong*: invalid inputs, missing records, DB issues, etc.
	* Without handling → you get ugly *500 stack traces* in API response.
	* With handling → you return *clear, standardized JSON error responses* (like an API contract for errors).

---
 2. Typical Classes in Exception Package
	a) *Custom Exceptions*
	We create *business/domain-specific exceptions* instead of throwing generic Java exceptions.

👉 Example:
	```java
	package com.shak.refdata.exception;

	public class ResourceNotFoundException extends RuntimeException {
		public ResourceNotFoundException(String message) {
			super(message);
		}
	}
	```
Usage:
	* If client requests an `Instrument` that doesn’t exist → throw `ResourceNotFoundException`.
	* This is cleaner than returning `null`.

---
	b) *Error Response Model*
	Define a standard JSON structure for errors.

👉 Example:

	```java
	package com.shak.refdata.exception;

	import java.time.LocalDateTime;

	public class ApiError {
		private LocalDateTime timestamp;
		private int status;
		private String error;
		private String message;
		private String path;

		public ApiError(int status, String error, String message, String path) {
			this.timestamp = LocalDateTime.now();
			this.status = status;
			this.error = error;
			this.message = message;
			this.path = path;
		}

		// Getters & Setters
	}
	```

So every error looks like:

```json
{
  "timestamp": "2025-08-25T12:30:00",
  "status": 404,
  "error": "Not Found",
  "message": "Instrument not found with id: 10",
  "path": "/api/instruments/10"
}
```

---

	c) *Global Exception Handler*
	Use `@ControllerAdvice` to catch exceptions globally.

👉 Example:
	```java
	package com.shak.refdata.exception;

	import org.springframework.http.HttpStatus;
	import org.springframework.http.ResponseEntity;
	import org.springframework.web.bind.MethodArgumentNotValidException;
	import org.springframework.web.bind.annotation.ControllerAdvice;
	import org.springframework.web.bind.annotation.ExceptionHandler;

	import jakarta.servlet.http.HttpServletRequest;

	@ControllerAdvice
	public class GlobalExceptionHandler {

		// Handle ResourceNotFoundException
		@ExceptionHandler(ResourceNotFoundException.class)
		public ResponseEntity<ApiError> handleNotFound(ResourceNotFoundException ex, HttpServletRequest request) {
			ApiError error = new ApiError(
					HttpStatus.NOT_FOUND.value(),
					"Not Found",
					ex.getMessage(),
					request.getRequestURI()
			);
			return ResponseEntity.status(HttpStatus.NOT_FOUND).body(error);
		}

		// Handle Validation Errors
		@ExceptionHandler(MethodArgumentNotValidException.class)
		public ResponseEntity<ApiError> handleValidationErrors(MethodArgumentNotValidException ex, HttpServletRequest request) {
			String message = ex.getBindingResult().getAllErrors().get(0).getDefaultMessage();
			ApiError error = new ApiError(
					HttpStatus.BAD_REQUEST.value(),
					"Validation Error",
					message,
					request.getRequestURI()
			);
			return ResponseEntity.status(HttpStatus.BAD_REQUEST).body(error);
		}

		// Handle Generic Exceptions
		@ExceptionHandler(Exception.class)
		public ResponseEntity<ApiError> handleGeneric(Exception ex, HttpServletRequest request) {
			ApiError error = new ApiError(
					HttpStatus.INTERNAL_SERVER_ERROR.value(),
					"Internal Server Error",
					ex.getMessage(),
					request.getRequestURI()
			);
			return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(error);
		}
	}
	```

---

 3. Flow of Exception Handling in API
	1. User hits API with bad input (`POST /instruments` with blank ISIN).
	2. Validation fails (`@NotBlank` in DTO) → Spring throws `MethodArgumentNotValidException`.
	3. `GlobalExceptionHandler` catches it.
	4. Converts to *clean JSON response* using `ApiError`.
	5. Returns with correct HTTP status (400 Bad Request).

---

 4. Industry Benefits
	* ✅ *Consistency* → all errors look the same.
	* ✅ *Separation of concerns* → controllers only handle success paths.
	* ✅ *Debugging made easier* → every error includes `timestamp` + `path`.
	* ✅ *Future extensibility* → you can add error codes for frontend apps.

---

💡 So, in summary:

* *Custom Exceptions* → business/domain errors.
* *ApiError class* → standard error response format.
* *GlobalExceptionHandler* → centralizes error handling using `@ControllerAdvice`.

8. Search APIs
   * Implement search (by ISIN, ticker, exchange, currency)
   * Add pagination + sorting using `JpaSpecificationExecutor`

Perfect 👌 — let’s go deep and treat this like an *enterprise-grade design review* with the top 1% engineering mindset.
We’re not just writing code — we’re designing a *searchable, paginated, scalable read API* the way large-scale reference-data systems do it.

---

 🔍 Search API Design (for Instruments)

 1. *The Why*
	A financial reference-data service is useless if it can’t *query efficiently by business identifiers*.

Typical queries are:
	* *Exact identifiers* (e.g., “Give me the instrument with ISIN = `US0378331005`”).
	* *Filtered lists* (e.g., “All instruments traded on NASDAQ in USD”).
	* *Exploratory queries* (e.g., “All instruments with ticker starting with `AA`”).
	* *Paginated navigation* (e.g., browse 10 per page).
	* *Sorted results* (e.g., order by ticker ascending).

This mirrors *real capital markets systems* (Bloomberg, Refinitiv, Markit), where reference data queries need *search + filters + pagination*.

---
 2. *The How*

 🔹 `JpaSpecificationExecutor`
	Spring Data JPA ships with *`JpaSpecificationExecutor`*, which is basically a *DSL for dynamic query building*.
	Instead of writing one `findByIsinAndTickerAndExchange(...)` method for every permutation (impossible to scale), we compose *Specifications* at runtime:
	```java
	Specification<Instrument> spec = Specification
		.where(hasIsin(isin))
		.and(hasTicker(ticker))
		.and(hasExchange(exchange))
		.and(hasCurrency(currency));
	```

Think of it like building a *query tree* dynamically. Each `hasXxx` returns a `Predicate`, and Spring Data compiles that into SQL under the hood.

This is *cleaner than Criteria API* (which is verbose), and avoids *string-concatenated JPQL* (which is unsafe).


 🔹 Pagination & Sorting
	Spring gives us `Pageable` abstraction:

* `page` → zero-based index
* `size` → number of records per page
* `sort` → sort expression (multi-column supported)

Example request:
	```
	GET /api/instruments/search?ticker=AAPL&exchange=NASDAQ&page=0&size=10&sort=isin,asc
	```

This translates into SQL:
	```sql
	SELECT * FROM instruments
	WHERE ticker = 'AAPL'
	  AND exchange = 'NASDAQ'
	ORDER BY isin ASC
	LIMIT 10 OFFSET 0;
	```

→ That’s enterprise-ready out of the box.


 🔹 DTO + Mapper
	We map the *JPA Entity → Response DTO* so clients don’t see internal database artifacts.

This ensures:
	* *Encapsulation* (we can change DB schema without breaking clients).
	* *Validation* (via Request DTO).
	* *Future-proofing* (response can enrich with computed fields).

---
 3. *The Flow*

Let’s trace a request end-to-end:

 Request
	```
	GET /api/instruments/search?isin=US0378331005&currency=USD&page=0&size=5&sort=ticker,desc
	```

 Controller
	```java
	@GetMapping("/search")
	public ResponseEntity<Page<InstrumentResponseDto>> searchInstruments(
        @RequestParam(required = false) String isin,
        @RequestParam(required = false) String ticker,
        @RequestParam(required = false) String exchange,
        @RequestParam(required = false) String currency,
        Pageable pageable) {

    Page<InstrumentResponseDto> result = instrumentService
            .searchInstruments(isin, ticker, exchange, currency, pageable)
            .map(InstrumentMapper::toDto);

    return ResponseEntity.ok(result);
	}
	```

What happens here?
	User calls /search?isin=US0378331005&page=0&size=5&sort=ticker,asc.
	API passes these values down to service.
	Service builds query.
	Repository runs it.
	Results come back.

---
 Service
	```java
	Specification<Instrument> spec = Specification.where(InstrumentSpecification.hasIsin(isin))
			.and(InstrumentSpecification.hasTicker(ticker))
			.and(InstrumentSpecification.hasExchange(exchange))
			.and(InstrumentSpecification.hasCurrency(currency));

	return instrumentRepository.findAll(spec, pageable);
	```
	* We combine all filters together like LEGO blocks.
	  If some values are empty → they are ignored.
	Here:
	.where(...) starts with first filter.
	.and(...) keeps adding filters.
	pageable tells it page number, size, and sort.

---
 Repository
	```java
	public interface InstrumentRepository extends JpaRepository<Instrument, Long>, JpaSpecificationExecutor<Instrument> {
	}
	```
* Normally, repository only gives us basic things (find by id, find all).
* We add JpaSpecificationExecutor which allows us to filter results.
* `JpaSpecificationExecutor` gives us `findAll(Specification, Pageable)`.


---
 Specification
	```java
	public static Specification<Instrument> hasIsin(String isin) {
		return (root, query, cb) ->
				isin == null ? null : cb.equal(root.get("isin"), isin);
	}
	```

* These are little pieces of logic that say:
👉 "if user gave me a value, filter by it; else ignore."

* If isin == null → no filter applied.
* If isin = "US0378331005" → SQL WHERE isin = 'US0378331005'.

   * Validate each row & insert in batch
   * Return job result (success/failure counts)

Ways to achieve:
1. *Synchronous bulk upload*
2. *Asynchronous bulk upload*

---1---Synchronous Bulk Upload

✅ 1. Synchronous Bulk Upload
---
* *Synchronous = Happens in one request-response cycle.*
  Client uploads a CSV file → Server processes the file (parse, validate, save to DB) → Server responds with success/failure report.
* The client waits until the server finishes.
* Best when:
  * File size is *small to medium* (few thousand records).
  * You want *immediate feedback*.
  * No need for background job tracking.

---

 ✅ 2. Flow of Synchronous Bulk Upload

 Step 1: Client Sends File
	* Request: `POST /api/instruments/upload`
	* Content-Type: `multipart/form-data`
	* Key: `file` → attach CSV


 Step 2: Controller Layer
	* Accepts file (`MultipartFile`)
	* Calls `InstrumentService.bulkUpload(file)`
	- *Controller role* = Just a bridge between client & service.


 Step 3: Service Layer (Core Logic):
	📂 `InstrumentService.bulkUpload(file)`
	1. *Read CSV*
	   * Using `BufferedReader` + `CSVParser` (Apache Commons CSV).
	   * `withFirstRecordAsHeader()` → allows us to use column names (`isin`, `cusip`, etc.) instead of hardcoded indexes.

	2. *Iterate Over Records*
	   * For each row, extract fields.
	   * Create `Instrument` entity.
	   * Add to a `List<Instrument>` for batch save.

	3. *Validate*
	   * If a row is missing a required field → mark as failure.
	   * Catch exceptions → track error messages.

	4. *Persist*
	   * At the end, call `instrumentRepository.saveAll(instruments)`.
	   * Saves all records in one go (batch insert, more efficient than one by one).

	5. *Return Result*
	   * Create a `BulkUploadResult` DTO → contains:
		 * `successCount`
		 * `failureCount`
		 * `errors` (list of strings describing failed rows).


 Step 4: DTO for Response
📂 `BulkUploadResult.java`
	Ensures client always gets a *structured JSON response*.


 ✅ 3. Key Concepts Behind the Code

* *`MultipartFile`*
  * Spring Boot abstraction for handling uploaded files.
  * Allows reading file stream directly (instead of writing to disk).

* *`Apache Commons CSV`*
  * Library to parse CSV safely.
  * Better than `String.split(",")` because it handles quotes, trimming, headers.

* *Batch Insert (`saveAll`)*
  * Saves a *list of entities in one DB transaction*.
  * Much faster than multiple `save()` calls.

* *Error Handling*
  * Wraps row parsing in `try-catch` so one bad record doesn’t stop the whole file.

* *DTO Response*
  * Separates internal logic from API contract.
  * Makes response predictable & easy to consume.

---2---Asynchronous Bulk Upload

Why Asynchronous Bulk Upload?
* *Synchronous (blocking)*:
  * Client uploads a CSV.
  * API parses + saves all rows before responding.
  * If file is large (say 10,000+ rows), the client waits (can timeout).
  * Good for *small uploads*, bad for scalability.

* *Asynchronous (non-blocking)*:
  * Client uploads a CSV.
  * API immediately creates a *job record* (`PENDING`) and returns jobId.
  * A *background thread* picks up the file, processes it, and updates job status.
  * Client can check progress via `/status/{jobId}`.
  * Standard in *enterprise apps* (batch imports, ETL, data migration).

---
 ️ Key Concepts in Our Implementation"

 1. Job Tracking
	We created an *entity `BulkUploadJob`* to store:
	* `status` (PENDING, IN\_PROGRESS, COMPLETED, FAILED)
	* counts (success/failure rows)
	* error log
	* timestamps

 This makes the process *auditable* and *trackable*.


 2. Async Execution with `@Async`
	Spring Boot lets us run methods in a *background thread pool* using `@Async`.
	We also enable it with `@EnableAsync` at the service level.
	
	```java

	public CompletableFuture<Void> processJob(Long jobId, MultipartFile file) {
		// runs in background
	}
	```
👉 Benefits:
	* Immediate HTTP response to client (no waiting).
	* Processing happens in a separate thread.
	* Client polls for status.


 3. DTO Layer
	We don’t expose JPA entities directly.
	Instead, we map `BulkUploadJob` → `BulkUploadJobResponse` DTO for API response
	This ensures *API stability* even if our entity changes.


 4. File Parsing (CSV)
	We reused *Apache Commons CSV* parser (same as synchronous upload), but wrapped in a background job:

	```java
	CSVParser csvParser = new CSVParser(reader, CSVFormat.DEFAULT
		.withFirstRecordAsHeader()
		.withIgnoreHeaderCase()
		.withTrim());

	for (CSVRecord record : csvParser) {
		try {
			Instrument instrument = new Instrument();
			instrument.setIsin(record.get("isin"));
			// set other fields...
			instruments.add(instrument);
			successCount++;
		} catch (Exception e) {
			failureCount++;
			errorLog.append("Row ").append(record.getRecordNumber())
					.append(": ").append(e.getMessage()).append("\n");
		}
	}
	instrumentRepository.saveAll(instruments);
	```
	 We batch save(means saving in one go) instruments for performance.

10. Auditing
    * Enable JPA Auditing (`createdBy`, `updatedBy`, timestamps)
    * Store change history in `instrument_audit` table (or Envers)
	
Perfect question 🙌 — let’s pause coding and break down the *concepts + important lines of code* around *Auditing in Spring Boot*.
We’re doing *two levels of auditing*:

---

 1. JPA Auditing (Created/Updated by & timestamps)

 Concept

* Spring Data JPA provides a built-in mechanism to automatically populate *audit fields* (`createdAt`, `updatedAt`, `createdBy`, `updatedBy`) for every entity.
** It uses *listeners* that trigger on `INSERT` and `UPDATE`.
* Requires us to:
  1. Enable auditing via `@EnableJpaAuditing`.
  2. Provide an *AuditorAware* bean (tells JPA who the current user is).
  3. Annotate fields in entities with `@CreatedDate`, `@LastModifiedDate`, etc.

---

 Code Walkthrough

📂 `AuditConfig.java`
	```java
	@Configuration
	@EnableJpaAuditing(auditorAwareRef = "auditorAware")
	public class AuditConfig {
		@Bean
		public AuditorAware<String> auditorAware() {
			return new AuditorAwareImpl();
		}
	}
	```
* `@EnableJpaAuditing` → turns on Spring Data JPA auditing.
* `auditorAwareRef = "auditorAware"` → tells Spring to use our custom bean to resolve the username.


📂 `AuditorAwareImpl.java`
	```java
	public class AuditorAwareImpl implements AuditorAware<String> {
		@Override
		public Optional<String> getCurrentAuditor() {
			// Ideally fetch from Spring Security context
			return Optional.of("system-user");
		}
	}
	```
* Returns the current user performing the action.
* Later, when we add security, we’ll replace `"system-user"` with the logged-in username.


📂 `BaseEntity.java`
	```java
	@MappedSuperclass
	@EntityListeners(AuditingEntityListener.class)
	public abstract class BaseEntity {

		@CreatedDate
		@Column(updatable = false)
		private LocalDateTime createdAt;

		@LastModifiedDate
		private LocalDateTime updatedAt;

		@CreatedBy
		@Column(updatable = false)
		private String createdBy;

		@LastModifiedBy
		private String updatedBy;

		// Getters/Setters...
	}
	```
* `@MappedSuperclass` → these fields are inherited by all child entities.
* `@EntityListeners(AuditingEntityListener.class)` → hooks into JPA lifecycle.
* `@CreatedDate` / `@LastModifiedDate` → auto-populate timestamps.
* `@CreatedBy` / `@LastModifiedBy` → auto-populate users from `AuditorAware`.


📂 `Instrument.java`
	```java
	@Entity
	@Table(name = "instrument")
	public class Instrument extends BaseEntity {
	   ...
	}
	```

* Extends `BaseEntity` → inherits auditing fields.

✅ Now, whenever you `save()` or `update()`, Spring automatically sets:
* `createdAt`, `createdBy` → when record is first created.
* `updatedAt`, `updatedBy` → when record is modified.

---

 2. Hibernate Envers (Change History Tracking)

 Concept

* JPA auditing only tells you the *latest state* (`who created`, `who updated`, `when`).
* If you want *full history* of every change (before & after values), you need Hibernate Envers.
* Envers maintains special `_AUD` tables to track all revisions:

  * `<entity>_AUD` → row-by-row change history.
  * `revinfo` → revision metadata (who/when).

Example:
* Insert → `_AUD` row with `REVTYPE = 0`.
* Update → new `_AUD` row with `REVTYPE = 1`.
* Delete → new `_AUD` row with `REVTYPE = 2`.

---

 Code Walkthrough

📂 `pom.xml`
	```xml
	<dependency>
		<groupId>org.hibernate.orm</groupId>
		<artifactId>hibernate-envers</artifactId>
	</dependency>
	```
* Pulls in Hibernate Envers module.


📂 `Instrument.java`
	```java
	@Entity
	@Table(name = "instrument")
	@Audited
	public class Instrument extends BaseEntity {
		...
	}
	```
* `@Audited` → tells Envers to track this entity’s changes in a history table.

---

 How it works:

1. You save a new instrument → row created in:
   * `instrument` (current state).
   * `instruments_AUD` (historical snapshot).
2. You update the instrument → Envers inserts a *new row* in `instruments_AUD`.
3. You delete the instrument → Envers inserts another *row* with `REVTYPE = 2`.

---

 ✅ Difference Between JPA Auditing & Envers

| Feature      | JPA Auditing                               | Hibernate Envers                            |
| ------------ | ------------------------------------------ | ------------------------------------------- |
| *Purpose*  | Track who & when                           | Track full history of changes               |
| *Fields*   | createdBy, updatedBy, createdAt, updatedAt | Complete snapshots of entity at each change |
| *Storage*  | Same table                                 | Separate `<entity>_AUD` + `revinfo` tables  |
| *Good for* | Metadata (latest info)                     | Audit trails, regulatory compliance         |

---

 🚀 Summary

* *JPA Auditing* → lightweight, adds metadata columns (`createdBy`, `updatedBy`, `timestamps`).
* *Envers* → heavyweight, keeps *entire history* of all changes in audit tables.
* Together, they give: *“who, when, what changed”*.
